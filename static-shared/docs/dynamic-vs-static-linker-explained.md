## 1. What Problem Does This Code Solve?

This project loads ELF shared objects (`.so` files built for ARM Cortex-M) into
RAM on a bare-metal microcontroller — no operating system, no `mmap`, no
userspace/kernel split. The loaded library must be able to call functions in the
main firmware image (`printf`, `sinf`, `operator new`), and functions in other
loaded libraries (`lib_a` calling into `lib_b`).

The loader described here is the **static patcher** (`scl::static` in
`src/static/`, plus the `scl::xip-static` execute-in-place flavour): it parses
the `.so` with the shared ELF32 reader in `common-elf-reader`, patches the
library's GOT/PLT and the main firmware's GOT in place at load time, runs
`.init_array` constructors, resolves every name eagerly, and records every word
it writes into the firmware's memory in a patch journal so `unload()` can
restore pristine state.

The original document contrasted this patcher with a runtime dynamic linker —
lazy binding, per-library GOT, r10 swapping. That side of the comparison is out
of scope here; this document describes only the static method.

## 2. Background: GOT, PLT, and Position-Independent Code

### The Problem

A shared object is compiled as position-independent code (PIC). The compiler
doesn't know at compile time where in memory the library will be loaded. Yet the
library needs to access its own global variables and call functions in other
libraries or the main firmware.

### The GOT (Global Offset Table)

The **GOT** is an array of 32-bit pointer slots that lives in the library's
data section. Every reference to a global variable or imported function goes
*through* the GOT:

```
// Instead of reading AA directly:
ldr r0, [pc, #offset_to_AA]   // wrong — AA's address is unknown

// The compiler emits:
ldr r0, [r10, #got_offset]    // r10 holds the GOT base address
                               // reads the *current address* of AA
```

On Cortex-M with `-msingle-pic-base -mpic-register=r10`, the register `r10`
always holds the GOT base address of the **currently executing library**. When
execution enters a library (via a trampoline or PLT), `r10` is set to that
library's GOT base. Every global-variable access becomes `ldr rd, [r10, #N]`.

### The PLT (Procedure Linkage Table)

The **PLT** is a small stub (a few instructions) generated by the linker for
every imported function call. It looks like:

```
func_foo_plt:
    movw ip, #lower(GOT[n])     ; ip = &GOT[n]
    movt ip, #upper(GOT[n])
    ldr  pc, [ip]               ; jump to whatever address is in GOT[n]
```

This is an indirect call through the GOT. The caller doesn't care *where* `foo`
actually lives — it reads the address from the GOT slot and jumps there.

### How the GOT and PLT Interact

```
   caller
     │
     │  bl func_foo_plt
     ▼
   ┌─────────────┐
   │  PLT stub   │  Loads ip = &GOT[n], then ldr pc, [ip]
   └──────┬──────┘
          │
          ▼
   ┌─────────────┐
   │  GOT[n]     │  Contains the *address* of func_foo
   └──────┬──────┘
          │
          ▼
   ┌─────────────┐
   │  func_foo   │  The real function
   └─────────────┘
```

### Why Is a PLT Needed If the Address Is Already in the GOT?

This is one of the most common questions about dynamic linking. If the GOT
already holds the address of every imported function — and the caller could
just read the address and jump — why have a PLT at all?

#### Reason 1: Code cannot be patched; data can

On Cortex-M, the code section (`.text`) typically lives in **flash** — read-only
memory that cannot be modified at runtime. The GOT lives in **RAM** (writable).
The compiler emits `BL func_foo` as a direct branch in the code. If the loader
later needs to change where `func_foo` points (e.g., because a library was
loaded and provides a better implementation, or because lazy binding resolved
the address on first call), it would have to rewrite the `BL` instruction in
flash — **impossible**.

The PLT solves this: the `BL` instruction in the caller's code never changes.
It always branches to a **fixed stub** in the PLT. The PLT stub is a tiny,
position-independent code sequence:

```asm
func_foo_plt:
    movw ip, #lower(GOT[n])      ; 2 instructions to form &GOT[n]
    movt ip, #upper(GOT[n])
    ldr  pc, [ip]                ; 1 instruction to load and jump
```

This never changes. Only the GOT slot changes — and since the GOT is in RAM,
that's trivially writeable.

#### Reason 2: The `BL` instruction has limited range

The ARM `BL` (branch-and-link) instruction encodes a **signed 24-bit offset**
(±32 MB). On Cortex-M, `BL` in Thumb-2 mode has a range of ±16 MB. If the
target function lives in a different library loaded at an arbitrary RAM address,
it may be **millions of bytes away** — far beyond the branch range.

The PLT stub uses `ldr pc, [ip]`, which loads a **full 32-bit address** from
the GOT. This has no range limitation: any function anywhere in the 4 GB address
space can be reached.

#### Reason 3: ARM/Thumb interworking

On ARM, functions can be in ARM mode (4-byte instructions) or Thumb mode
(2-byte/4-byte mixed). Cortex-M is Thumb-only, but the PLT stub still handles
this cleanly: the loaded address from the GOT has the Thumb bit (bit 0) set,
and `ldr pc, [ip]` correctly enters Thumb mode. A direct `BL` to an address
without the Thumb bit would fault (`INVSTATE` exception). The PLT stub
abstracts this: the caller does `BL func_foo_plt` (a relative branch to a
nearby stub), and the stub handles the indirect jump with the correct mode bit.

#### Summary

| Concern | Without PLT | With PLT |
|---|---|---|
| Patching the target at runtime | Must patch flash (impossible) | Patch GOT in RAM |
| Range of call | Limited to ±16–32 MB from the call site | Full 32-bit address space |
| ARM/Thumb interworking | Caller must manage mode bit | PLT stub handles it |
| What is the `BL` target? | The real function (unknown until load time) | The PLT stub (known at link time) |


### Reserved GOT Slots

By ARM ELF convention, the first 3 GOT entries are reserved:

| Slot | Name | Purpose |
|---|---|---|
| GOT[0] | — | Address of the `.dynamic` section |
| GOT[1] | — | Link-time identification (not used at runtime) |
| GOT[2] | — | Address of the lazy-resolution trampoline (`dl_runtime_resolve`) |

Data slots start at GOT[3].

| | `scl::static` (`src/static/`) |
|---|---|

| **Cross-lib GOT base** | Not applicable — all addresses are absolute |

## 4. `scl::static` — The Static Patcher (`src/static/`)

### Why It Exists

This loader was originally written to load and test shared libraries from a
host PC environment, where the full C++ runtime, heap, and standard library are
available — so it can use `std::vector`, `std::unique_ptr`, and a patch journal.
The name "static" refers to the *resolution strategy* — all names are resolved
at once, like a static linker would do — not to the build-time vs run-time
distinction.

### How Loading Works (`Module::load_file`, `src/static/module.cpp`)

**Step 1: Parse the ELF header.** `elf_reader::open_elf()` (`src/static/elf-reader.cpp`)
wraps `loader::elf_image::parse()` from `common-elf-reader`: it validates the
ELF header, confirms it's a 32-bit ARM shared object, and stores the header in
memory.

**Step 2: Compute base virtual address.** The lowest vaddr across all `PT_LOAD`
segments is the load bias. The test fixtures are linked at vaddr 0, so the final
loaded address of a symbol is simply `buffer + st_value`.

**Step 3: Load the image.** `shlib_loader::load_bin()` (`shlib-loader.cpp:56`)
walks the `PT_LOAD` program headers and copies `p_filesz` bytes into the
caller-provided RAM buffer at their `p_vaddr` offsets, zeroing the BSS tail
(`p_memsz - p_filesz`). `get_binary_size()` (the highest `PT_LOAD` end) must fit
the buffer or `INVALID_SEGMENT` is returned. `scan_dependencies()` collects the
`DT_NEEDED` sonames.

**Step 4: Build a relocation plan.** `find_shlib_symbols_to_patch()` and
`find_main_symbols_to_patch()` (`shlib-loader.cpp`) stream `.rel.dyn` +
`.rel.plt` and the dynamic symbol table into flat `symbol_patch` arrays — one
entry per relocation — each carrying `{name, got_address, virtual_address, type,
index, binding}`. The array sizes are queried first via
`calculate_patch_array_size`.

**Step 5: Apply the plan to the library.** `patch_shlib()` (`shlib-loader.cpp:301`)
writes into the *library's* RAM image:

- `R_ARM_RELATIVE` → `*slot += base` (self-referential offsets),
- `R_ARM_ABS32` → `*slot = resolve(name)` (e.g. `.init_array` entries),
- `STB_GLOBAL`/`STB_WEAK` (`GLOB_DAT`/`JUMP_SLOT`) → `*slot = resolve(name)`.

Every write is bounds-checked against the image size. `JUMP_SLOT`s are resolved
eagerly — **not** left for lazy binding.

**Step 6: Patch main firmware's GOT.** `patch_main()` (`shlib-loader.cpp:463`)
reads the *firmware's* `.rel.dyn` section (via the `_reloc` block emitted by the
firmware linker script). For every JUMP_SLOT or GLOB_DAT entry whose symbol is
defined in the newly loaded library, it writes the library-provided absolute
address into the firmware's GOT slot, handling `R_ARM_COPY` (main's slot ←
library symbol address). Every write is recorded in the patch journal. This is
how `printf` calls from main can resolve to a library-provided replacement, or
vice versa.

**Step 7: Run constructors.** `execute_constructors()` (`shlib-loader.cpp:572`)
locates the library's `.inits` (falling back to `.init_array`) and calls each
function pointer, then `sync_after_patching()` issues the memory barrier
(DSB/ISB) so the newly written GOT/PLT words are visible to the instruction
path.

**Step 8: Dependency resolution.** `resolve_dependencies()` (`shlib-loader.cpp`)
auto-loads the library's `DT_NEEDED` dependencies via the app-provided
`dep_loader` callback, resolving imports that only the new library provides.

### How Symbol Resolution Works

The resolution order is fixed and hardcoded in `patch_shlib()`:

1. Self-defined (`st_value != 0`) → `buffer + st_value`.
2. The shared `symbol_table` → address registered by an earlier library
   (cross-module interposition, first-loaded-wins).
3. The firmware's own `.dynsym` (`find_symbol_address()`), read through the
   `_reloc` block.

Weak symbols follow the same order but are legal to resolve to `0` (undefined
weak). Exported symbols are *published* into the `symbol_table` during
`patch_shlib`, which is how later-loaded libraries reach earlier ones.
`Module::sym()` offers a name → address lookup over the loaded `.dynsym` that is
hash-accelerated by the SysV `.hash` section (with a linear fallback).

### How Unloading Works

`Module::unload()` (`src/static/module.cpp`) is reference-counted
(`retain()`/`release()`, teardown at 0):

1. **Run destructors** (`.fini_array`) and **revert the journal**: every word
   written into the firmware's memory is restored to its original value (pop
   order, so the last patch written is the first restored). This restores the
   firmware's GOT to its pre-load state.
2. **Unpublish exports**: symbols this module published into the shared
   `symbol_table` are removed.
3. **Release the buffer**: the module's state is reset and the caller-owned
   RAM buffer is released.

The journal-based revert is essential here because patches go directly into the
*firmware's own memory* (its GOT, its data sections), not into an isolated
arena. Without the journal, unloading would leave corrupted state.

### The `scl::Module` API

The `scl::static` loader is fronted by the `scl::Module` class
(`include/static/module.h`):

```cpp
scl::Module mod;
mod.load_file("libfoo.so", ram_buf, sizeof ram_buf, &g_syms);
```

#### `load_file(path, exec_buf, exec_sz, syms, scope, dep_loader)` — Load a library

Takes a file path (or `load_buf()` takes an in-memory buffer) and a
caller-provided RAM buffer. Returns true on success. Internally it:

1. Parses the ELF (`elf_reader` over `loader::elf_image`).
2. Loads the `PT_LOAD` segments into the buffer (`shlib_loader::load_bin`).
3. Resolves the helper sections (`.inits`, `.rel.dyn`, `.rel.plt`, `.dynsym`,
   `.dynstr`, `.hash`).
4. Enumerates the library's and the firmware's fixups
   (`find_*_symbols_to_patch`).
5. Applies them — `patch_shlib` then `patch_main` (resolves all symbols
   eagerly, journals every write).
6. Runs constructors (`execute_constructors` + memory barrier).
7. Auto-loads `DT_NEEDED` dependencies (`resolve_dependencies`).

Errors are reported through `module_error` / `last_error_string()` — there is no
error-string-based C API.

#### `unload()` — Unload a library

Reverts the journal (byte-exact), runs `.fini_array` destructors, unpublishes
exports, and releases the buffer. Reference-counted via `retain()`/`release()`.

#### `sym(name)` / `operator[]` — Resolve Symbol Name to Address

Searches the loaded module's own `.dynsym`/`.dynstr`/`.hash` triple
(hash-accelerated, with a linear fallback), returning the image-relative
`st_value` turned into an absolute address. `operator[]` wraps this in a
callable functor so `mod["func"](arg)` works.

## 5. How the GOT Is Used by the Static Patcher

### `scl::static` — Direct GOT Patching

The static patcher writes absolute addresses directly into the firmware's
existing GOT slots — there is no per-library r10 register, no GOT-base
swapping, and no indirection through a runtime trampoline. The library's own
GOT (in the loaded RAM buffer) is patched by `patch_shlib`; the firmware's side
is handled by `patch_main`.

```
Host firmware's GOT (single, shared):

  GOT[0]   .dynamic addr
  GOT[1]   (reserved)
  GOT[2]   dl_runtime_resolve (if lazy mode; usually not used)

  GOT[3]   printf     ← address of host's printf()
  GOT[4]   sinf       ← address of host's sinf()
  ...
  GOT[N]   lib_func   ← written by patch_main() to point into the loaded library
```

When `patch_main()` runs, it iterates the firmware's `.rel.dyn` (via the
`_reloc` block) and writes the loaded library's absolute function addresses
into the firmware's GOT slots. After that, any code in the firmware that calls
`lib_func()` via the PLT will jump directly to the library's code.

There is no mechanism to swap context — the library must be compiled
compatibly with the firmware's PIC model (the `-fPIC` fixtures), or the
addresses are adjusted appropriately.

## 6. Step-by-Step: Loading a Library

### `scl::static` (on target)

```
Module::load_file("libfoo.so", buf, bufsz, &g_syms)
  │
  ├─ 1. Parse ELF header (elf_reader over loader::elf_image)
  ├─ 2. Find ".dynsym" / ".dynstr" section idx (must be a dynamic .so)
  ├─ 3. shlib_loader::load_bin — copy PT_LOAD segments into the RAM buffer (zero BSS)
  ├─ 4. populate_helper_sections — locate .inits / .rel.dyn / .rel.plt / .dynsym / .dynstr / .hash
  ├─ 5. find_shlib_symbols_to_patch + find_main_symbols_to_patch — enumerate fixups
  ├─ 6. patch_shlib — patch the library's GOT:
  │     RELATIVE → *slot += base; ABS32 / GLOB_DAT / JUMP_SLOT → *slot = resolve(name)
  │     publish exports into the shared symbol_table
  │     (JUMP_SLOTs are resolved eagerly, NOT left for lazy binding)
  ├─ 7. patch_main — iterate the firmware's .rel.dyn, write lib addresses into main's GOT (journaled)
  ├─ 8. execute_constructors — run .init_array, then memory barrier
  ├─ 9. resolve_dependencies — DT_NEEDED auto-load
  └─10. Return module
```

## 7. Test Infrastructure: Where Tests Run and What They Test

The project has a **two-tier** test setup: host-unit tests (no hardware needed)
and on-target firmware tests (need a WeAct BlackPill STM32F411CE board +
OpenOCD, or a NUCLEO-F411RE, or `qemu-system-arm`). The `scl::static` loader
builds on the shared ELF32 core in `common-elf-reader`; the tests at both levels
validate that shared core.

### Tier 1: Host-Only Unit Tests

**Where they run**: On your development PC (Linux, macOS, Windows). No board,
no semihosting, no cross-compiler needed.

**Compiler**: Your system's native `g++` / `clang++` (e.g. `x86_64-linux-gnu-g++`).

**What they test**: The portable ELF core the static patcher builds on — the
ELF parser (`loader::elf_image` in `common-elf-reader`), SysV-hash symbol
lookup, and the relocation-apply logic:

| Suite | What it tests |
|---|---|
| **dynamic1** | ELF header validation, program/section header reading, `find_section()` by name, `image_size()` computation, `dynamic_info` parsing |
| **dynamic2** | SysV hash lookup: find defined symbols, report externals as value=0, reject absent names |
| **dynamic3** | Relocations: applying RELATIVE/GLOB_DAT/JUMP_SLOT/ABS32/REL32/COPY via the reloc applier, overflow detection |
| **dynamic4** | Region allocator (arena) |
| **dynamic5** | Load simulation over real `.so` fixtures, negative tests (truncated ELF, unknown reloc type, cyclic hash) |

**Crucially**: these suites test ONLY the shared core. They do NOT test the
`scl::static` pipeline (`src/static/shlib-loader.cpp`). That is exercised
on-target in Tier 2.

Why "dynamic1–5" despite testing shared code? Historical naming: the common
core was originally developed alongside the loader, so the host unit-test
suites were prefixed "dynamic". They primarily validate the shared core, not
the `scl::static` pipeline.

## 8. How Complete Is the ELF32 Parser?

**Short answer: not a complete ELF32 parser.** It covers only the subset
needed to load ARM shared objects into an embedded Cortex-M system, and
explicitly rejects everything else. The design is minimal-by-necessity: the
parser runs on bare-metal with no heap, no file I/O library, and extremely
limited RAM.

### What It Parses

| ELF component | What the parser does |
|---|---|
| **ELF header (`Ehdr`)** | Validates magic (`0x7fELF`), class (32-bit), endianness (LE), machine (ARM), type (shared object). Reads all fields into an in-memory struct. |
| **Program headers (`Phdr`)** | Reads individual `PT_LOAD` entries on demand to compute image size/footprint and to copy segments into the arena. Non-`PT_LOAD` program headers are skipped silently. |
| **Section headers (`Shdr`)** | Reads individual section headers on demand via `section_header(index)`. `find_section(name)` scans all sections to locate `.dynsym`, `.dynstr`, `.hash`, `.rel.dyn`, `.rel.plt`, `.got`, `.init_array`, `.fini_array`, `.ARM.exidx` by name. |
| **Symbol table (`.dynsym`)** | Treated as an array of `elf::Sym` (16 bytes each). Individual entries are read via `load_word` into the 3 fields needed: `st_name`, `st_value`, `st_size`, `st_info`. |
| **String table (`.dynstr`)** | Random-access NUL-terminated string lookups via `name_at()` (a bounds-checked `strnlen` equivalent). |
| **Hash table (`.hash`)** | Implements the classic SysV ELF hash algorithm: `nbucket` / `nchain` / bucket array / chain array. Walks the chain until a match or chain end. |
| **Dynamic section (`_DYNAMIC`)** | Parses the `DT_NULL`-terminated array of `Dyn` entries to extract `DT_HASH`, `DT_SYMTAB`, `DT_STRTAB`, `DT_STRSZ`. |
| **Relocation entries (`Rel`)** | Reads raw 8-byte entries (the ARM REL format — no `r_addend`). Classifies 6 types via `r_type()`, extracts the symbol index via `r_sym()`. |

### What It Does NOT Parse (Deliberately)

| ELF feature | Status | Why excluded |
|---|---|---|
| **RELA relocations** | Not supported | ARM uses `REL` format (addend is in-place in the image word, not in `r_addend`). RELA (used by x86-64, AArch64) has no addend-in-place and would give wrong results. |
| **GNU hash (`.gnu.hash` / `DT_GNU_HASH`)** | Not supported | Only SysV `.hash` is parsed. Libraries built with `--hash-style=gnu` or `both` are rejected (symbol lookup silently fails). All project `.so` files use `--hash-style=sysv`. |
| **`.init` / `.fini` sections (old-style)** | Not supported | Only `.init_array` / `.fini_array` (section type `SHT_INIT_ARRAY` = 14, `SHT_FINI_ARRAY` = 15) are recognized. The old `SHT_PROGBITS` `.init` section with a single function pointer is not. |
| **`.preinit_array`** | Not supported | The dynamic linker spec defines a pre-initialization array; this loader ignores it. |
| **TLS (thread-local storage)** | Not supported | No `R_ARM_TLS_*` relocation types are handled. Cortex-M bare-metal has no thread-local storage model. |
| **Debug sections (`.debug_*`, `.stab*`)** | Ignored | The parser skips non-`SHF_ALLOC` sections by default. Debug info is never read. |
| **NOTE segments / sections** | Ignored | `PT_NOTE` program headers and `SHT_NOTE` sections are skipped. |
| **`.ARM.attributes`** | Ignored | The section exists in the test fixtures but is never read. ABI-flag validation (soft vs hard float) is not done at the ELF level — the test scripts (`verify-test-libs.sh`) check this out of band. |
| **`.comment` / `.note.gnu*`** | Ignored | Toolchain metadata is never parsed. |
| **`SHT_DYNAMIC`** | Only `_DYNAMIC` | The dynamic section is read via the `_DYNAMIC` linker symbol in the *firmware*, not from the loaded library. The loaded library's `.dynamic` is not parsed — the loader instead reads `.dynsym`/`.dynstr`/`.hash` sections directly by name. |
| **`PT_DYNAMIC`** | Not used | The program-header-based dynamic segment is not read. |
| **`PT_GNU_EH_FRAME`** | Not used | The GCC EH frame header is not needed — exception handling uses EHABI (`PT_ARM_EXIDX`). |
| **`PT_GNU_STACK`** | Not used | Stack executability is irrelevant on bare-metal. |
| **`PT_GNU_RELRO`** | Not enforced | The relro segment is present in the test .so files but the loader does not mprotect pages (no MMU). |
| **`.interp` section** | Ignored | Not relevant — there is no dynamic linker to invoke. |
| **`.gnu.version` / `.gnu.version_r`** | Ignored | Versioning information is not checked. |
| **Symbol visibility (`.dynsym` `st_other`)** | Ignored | `STV_HIDDEN`, `STV_PROTECTED`, `STV_DEFAULT` are all treated identically. |
| **`R_ARM_GOT32`, `R_ARM_PLT32`, etc.** | Not supported | These are linker-emitted relocations used during the link step, not at load time. The loader only handles the 6 runtime relocation types. |
| **`R_ARM_THM_*` relocations** | Not supported | The compiler/linker resolves Thumb-specific relocations at build time; they should not appear in the final `.so`. |
| **64-bit ELF (ELFCLASS64)** | Explicitly rejected | The parser requires `EI_CLASS == 1` (32-bit). |
| **Big-endian (ELFDATA2MSB)** | Explicitly rejected | The parser requires `EI_DATA == 1` (little-endian). |
| **Non-ARM architectures** | Explicitly rejected | `e_machine` must be `40` (ARM). |
| **Relocatable objects (ET_REL)** | Explicitly rejected | `e_type` must be `3` (shared object). Executables (ET_EXEC) and core files (ET_CORE) are also rejected. |

### Relocation Types: What's Handled vs What's Missing

**Handled** (the 6 ARM runtime relocations that appear in a fully-linked `.so`):

| Type | Value | Used for |
|---|---|---|
| `R_ARM_RELATIVE` | 23 | Base-relative fixups (string pointers, vtable, constructor pointers) |
| `R_ARM_GLOB_DAT` | 21 | GOT entries for imported global variables |
| `R_ARM_JUMP_SLOT` | 22 | GOT entries for imported functions (PLT slots) |
| `R_ARM_ABS32` | 2 | Absolute 32-bit data references (constructor entries, static data) |
| `R_ARM_REL32` | 3 | PC-relative 32-bit references (EHABI typeinfo in `extab`) |
| `R_ARM_COPY` | 20 | Copy relocation for extern variables defined in main |

**Not handled** (would cause `INVALID_RELOCATION`):

- `R_ARM_GOT32` (link-time GOT formation)
- `R_ARM_PLT32` (link-time PLT formation)
- `R_ARM_GOTOFF` (link-time GOT-relative addressing)
- `R_ARM_GOTPC` (link-time GOT base computation)
- `R_ARM_THM_CALL`, `R_ARM_THM_MOVW_ABS_NC`, `R_ARM_THM_MOVT_ABS`, etc.
- `R_ARM_TLS_DTPMOD32`, `R_ARM_TLS_DTPOFF32`, `R_ARM_TLS_TPOFF32`
- `R_ARM_NONE`
- `R_ARM_V4BX`
- All other ARM relocation types (the ARM ELF ABI defines ~130 types)

The missing types are **link-time relocations** — they are resolved by the
linker when building the `.so` file and should never appear in the final
shared object's `.rel.dyn` / `.rel.plt` sections. If one does appear (e.g.,
from a misconfigured build), the loader rejects it cleanly.

### Design Philosophy

This is not a general-purpose ELF tool like `readelf` or `libelf`. It is a
**minimal loader core** with three priorities:

1. **Freestanding**: Compiles for Cortex-M bare-metal with no libc, no heap,
   no file I/O.
2. **Deterministic**: Fixed memory pools, no `std::vector`, no unbounded
   allocation.
3. **Fail-fast**: Every unsupported feature produces a clear error return
   (`INVALID_RELOCATION`, `SECTION_NOT_FOUND`, `NOT_AN_ELF`) instead of
   silently producing wrong results.

The parser validates the ELF header just enough to confirm it can handle the
file, then reads only the bytes it needs — individual program headers,
section headers by index, and relocation entries one at a time. It never
loads the entire ELF structure into memory.

## 9. Why This Approach?

### Historical / Development Context

The static patcher was the project's first approach. It was written to run on
a host PC for rapid prototyping and testing, where heap allocation and STL
containers are available. The name "static" reflects that the *resolution
strategy* is static — all names are resolved once at load time and patched in
place — even though the objects being loaded are `.so` files ("dynamic"
objects). In this repo the loader is `scl::static`.

### Fundamental Design Differences

**Why eager resolution with a journal:**
- Simpler to debug: all symbols are resolved immediately; no lazy surprises.
- The journal is needed because the firmware is a single process — patches go
  into its own memory space (its GOT, its data sections) and must be
  revertible.
- The firmware's symbol table (via the `_reloc` block) is passed to the loader
  without any hardcoded symbol mappings.

**Why it patches main's GOT:**
- The test firmware may not have a proper pre-linked `.dynsym` for everything a
  library needs. Library functions that override or extend main's symbols must
  be visible to main's PLT entries. `patch_main()` makes that happen by writing
  directly into the firmware's GOT slots.

### Summary Analogy

Think of `scl::static` as a **runtime linker** that behaves more like a static
linker running late: it reads all relocations, resolves every name immediately,
and writes final addresses directly into the running program's memory — then
keeps a journal so it can undo those writes on unload.

## 10. Suggestions for Improvement

These recommendations follow from the analysis above, ordered by impact.

### 1. Add GNU hash (`DT_GNU_HASH`) support to symbol lookup

Modern ARM toolchains emit `.gnu.hash` by default (`--hash-style=gnu` or
`both`). The current SysV `.hash` lookup reads only the legacy `.hash` section.
A library built without `--hash-style=sysv` will silently fail
(`SymbolNotFound`) on every lookup — a hard-to-diagnose bug.

**Implementation sketch:** Add an alternative lookup path in the symbol lookup.
Detect the `.gnu.hash` section by checking for `DT_GNU_HASH` in the `_DYNAMIC`
array (or by section name). The GNU hash format uses Bloom filters for fast
rejection and a different chain layout. Both hash tables can coexist — try gnu
hash first (faster), fall back to SysV.

**Test:** Add a CI build that links the test `.so` fixtures with
`-Wl,--hash-style=both` to exercise both paths.

### 2. Add `.init`/`.fini` legacy section support

Some embedded toolchains emit old-style `.init`/`.fini` sections — a single
function pointer in a `SHT_PROGBITS` section — instead of the newer
`.init_array`/`.fini_array` in `SHT_INIT_ARRAY` sections. The current code
finds constructors **only** by section type (`SHT_INIT_ARRAY`), missing `.init`
entirely.

**Fix:** After the type-based lookup fails, add a name-based fallback for
`.init` and `.fini`.

### 3. Add compile-time relocation-type coverage check

An unknown relocation type is currently a runtime error (`INVALID_RELOCATION`).
In a debug build, the loader could catch missing types at compile time with:

```cpp
template <std::uint8_t...> struct RelocSet {};
using HandledTypes = RelocSet<2, 3, 20, 21, 22, 23>;
// static_assert that classify() covers all elements of HandledTypes
```

Or more practically, a `switch` with GCC/Clang `-Wswitch` already catches
missing `enum class` values — the `classify()` function in the relocation path
should use a switch instead of an if-else chain.

### 4. Document the single-threaded assumption explicitly

The loader uses module-level state without any locking. This is correct for
bare-metal Cortex-M single-threaded firmware, but a reader from the Linux world
(where `dlopen` must be thread-safe) will assume a bug. An RTOS application can
define strong `scl_loader_lock()` / `scl_loader_unlock()` hooks to serialize
load/unload against other tasks.

**Fix:** Add a comment at the top of `module.cpp`, `shlib-loader.hpp`, and
`elf-reader.hpp`:

```cpp
// Thread-safety: this runs on bare-metal Cortex-M; an RTOS app defines strong
// scl_loader_lock()/scl_loader_unlock() to serialize load/unload.
```

### 5. Add CI for `--hash-style=both`

The test `.so` fixtures are built with SysV hash (`--hash-style=sysv`).
Nothing in CI builds them with `--hash-style=gnu` or `--hash-style=both`,
so a regression in SysV hash parsing or a missing GNU hash path would go
unnoticed until someone links a real library with default toolchain flags.

**Fix:** Add a CI step (or a CMake option) that rebuilds the fixtures with
`-Wl,--hash-style=both` and runs the host-unit tests against them. If
suggestion 1 (GNU hash support) is implemented, this CI step proves it works.
